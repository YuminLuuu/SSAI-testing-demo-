规范提炼 · 供本项目复用

提需求的骨架

从一份完整的八步实录里，把「怎么跟 AI 提需求」这件事拆成可以照着填的模板。重点不是流程图，是那四段格式完全相同的模块 prompt。

来源：SheShapesAI 工作坊实录（44 页），项目 Job Hunt Copilot，专家「海参」，12:30 → 21:00 一天走完八步。下面的引文均出自该材料。
坐标

八步，以及我们跳过了哪两步

Problem/Idea Define Co-create Prototype Evaluate Iterate Test Reflect
我们现在在这 我们跳过了

这是对照下来最该说的一件事：我们从 Problem/Idea 直接跳到了 Prototype。原型本身有用（它是用来验证信息架构的一次性道具），但按这套规范，Define 应该先写成文件、固化成项目的事实依据，之后每一次提需求都回指它。我们现在没有那份文件，所以每次对话都要重新交代一遍上下文——这正是这套规范要消灭的浪费。

材料原文 · 项目初始化 「Claude Code 里写 CLAUDE.md，把 Define 固化为项目事实依据。」后面每一个模块 prompt 的第一句都是「基于 CLAUDE.md 里的 Define 和已上线的 X 表结构……」
思考方式

专家在做的三个动作

这三个动作在材料里反复出现，而且顺序固定。它们发生在写任何 prompt 之前。

  1. 收到模糊需求，先拆解并逐块标风险，然后主动收窄

    面对一段一口气说完的痛点，没有直接给方案，而是拆成四块并分级：完全可行 / 可行，但这是红线活 / 中等风险 / 风险最高。然后给出收窄建议——关键是说清被砍掉的部分去了哪里，不是丢弃，是「作为 Reflect 阶段的下一步迭代方向，不在初始阶段实现」。

  2. 把用户的产品语言，逐条翻译成技术约束

    材料里管这叫「把藏着的技术要求拆出来」。格式统一是 用户的原话 → 技术含义，每条都能回指到用户说过的某句话。翻译完再收束成一句本质判断：「这个项目的本质是：一个需要关系型数据管理 + 文件存储 + 外部信息接入 + 受约束文本生成 + 未来多用户扩展能力的小型全栈产品。」

  3. 约束必须固化成机制，不能停在口头约定

    这是整份材料的价值观核心。「不能编造经历」这条红线，处理方式不是每次 prompt 里叮嘱一遍，而是做成自定义 Skill：「一次性 prompt 容易漏描述、每次结果不稳定；固化成规则组件才能保证每次生成都按同一套红线走。」最后验收时的原话是——红线约束「在代码和数据库层面都有实际机制守着，不只是口头约定」。

模板 T0

还没想清楚时，怎么开口

这是全篇第一个 prompt，用在「我知道我想要什么，但不知道能不能做」的阶段。

原文Problem / Idea
我现在有一个痛点是：「……原样贴上你的痛点，不要加工……」

我个人初步的感受是想做出来的东西都不是很复杂和困难，
但我不确定现有 AI 的捕捉能力是否可以实现我想解决的关键点
以及实现我想要的自动化程度。

请你充分思考我的需求并结合现有 AI 平台的能力，
给我一个更具体可行的初步方案。
原样贴
痛点不要自己先整理成条目。原始的、啰嗦的描述里包含你没意识到的信息，整理会把它们洗掉。
交代不确定
主动说出「我不确定的是 AI 的能力边界」。这一句把对方的任务从「照做」改成了「判断可行性」，是这个模板的全部价值所在。
要方案不要成品
请求的是「更具体可行的初步方案」，不是「帮我做出来」。这一步要的是收窄，不是交付。
模板 T1

Define：五件套，验收标准要可判定

确认收窄范围之后，下一句是：「请你基于该开发目标，帮我再次定义更清晰完整的问题描述。」产出固定包含五块——

块要求
目标用户一句话，具体到人。材料里就是「一位同时海投多个海内外岗位的求职者（我）」。
核心模块编号列出，每条说清存什么/做什么。
User story「作为 X，我想 Y，这样 Z」。Z 是收益，不能省。
验收标准逐条对应核心模块，且必须写成可判定的句子。这是五块里最关键的一块。
产出形式形态 + 使用范围 + 未来扩展预期。
一条验收标准的完整写法 「草稿里的每一处经历描述都能在个人信息库里找到对应事实来源（不能凭空生成信息库里没有的内容），生成结果是草稿，不自动发送，需要人工确认。」

一句话里塞了四样东西：正向要求、括号里的负向禁止、交付物的性质（草稿而非成品）、流程约束（人工确认）。负向禁止和流程约束是大多数人会漏掉的两样，而它们恰恰是后面能守住红线的原因。

模板 T2 · 核心

模块开发骨架

这个结构在材料里原封不动重复了四次（四个模块各一次）。重复四次意味着它不是即兴发挥，是一个模板。这是整份材料里最值得直接抄走的东西。

骨架Co-create · ×4
现在开发模块 N：模块名。
基于 CLAUDE.md 里的 Define 和已上线的 具体表名 表结构，
设计实现方案（先出方案，不要动手写代码）：

功能范围：
1. 做什么 + 边界 + 为什么
2. ……
3. 核心难点，请重点设计：……
4. 不提供 X，只提供 Y（对应之前 Z 的设计决定）

请给出：页面/路由结构、需要的组件、本模块难点具体怎么实现、
以及这些改动会新增/修改哪些文件。
基于……
锚定既有事实，不让对方重新发明上下文。点名到具体的表、具体的文件，而不是泛泛说「按之前说的」。
先出方案
强制把「想」和「做」切开，给自己留一道 review 关口。材料里每个模块都是 Plan → 人工 review → 才执行。
编号功能
编号是为了后面能逐条勾验收，不是为了好看。
影响面
「会新增/修改哪些文件」是这个模板里最容易被漏掉、但决定 review 质量的一句。不知道动了哪些文件，你就 review 不动。
技巧

功能条目里的三种高阶写法

把四段模块 prompt 横向比一遍，能看出三个反复出现、而且很难自己想到的动作。

一 · 标出核心难点，并明令禁止敷衍

「5. 请明确设计一个校验机制：如果 AI 生成的某段描述在结构化输出里没有对应的 citation，该怎么处理——是拒绝这段内容，还是标记为"未核实"提示用户重点检查？这是最需要守住的红线，请给出具体方案，不要笼统带过。」

三个动作叠在一起：标记优先级（「最需要守住的红线」）、给出候选让对方在里面选（而不是开放式提问）、明确禁止笼统。中间那条尤其值得学——把开放题变成选择题，回答质量会稳定得多。

二 · 写清楚「不要什么」，并回指到之前的决定

一般写法

「不要提供删除功能。」

材料里的写法

「不提供删除功能，只提供"归档"（把 status 改成 archived），对应之前 on delete restrict 的设计决定。」

差别在于后半句。它把这条禁令和之前某个决定绑在了一起，对方就知道这不是随口一说，改动时也会连带考虑那个决定。

三 · 主动阻止对方复用上一次的结论

「8. 请给出你建议用哪个模型做这个生成任务，并说明理由（这个任务对输出质量、指令遵循要求比模块 1 的 JD 解析要高，模型选择需要重新权衡，不要直接照搬模块 1 的 Haiku 选择）。」

这条最见功力。她预判到了对方会有惯性，于是提前把惯性点出来并禁止。凡是「上一个模块这么做过、但这个模块条件变了」的地方，都值得补这么一句。

模板 T3

架构设计：把未来的约束写进现在的要求

原文节选Plan Mode
请基于 CLAUDE.md 里的 Define 章节，设计数据库表结构方案，覆盖四个模块：……

要求：
1. 只出设计方案，不要执行/不要建表，我需要先 review。
2. 说明每张表的字段、类型、主键外键关系。
3. 说明表之间怎么关联（比如投递进展记录怎么关联到具体的岗位记录）。
4. 说明每张表需要的 RLS 策略，即使现在只有我一个用户，
   也要按"未来可能开放给多用户"的方式设计。
5. 素材库涉及文件存储，说明用哪种方式组织。
第 4 条
这是整段的精髓。现在不需要的能力，但未来一定会需要，就要在今天的设计里留出位置。理由在选型表里写得很直白：「现在改数据结构成本最低，等真的要开放时不用推倒重做，只是把权限开关打开。」
模板 T4 / T5

反馈和迭代，同样有格式

Evaluate：现象 → 判断 → 期望

四条评估结论的结构完全一致，而且每条都先承认能跑通的部分，再说问题，最后落到一句根因：

「确实可以根据具体的岗位信息来生成新的 CV 和 Cover letter，但是生成的文件有诸多问题，首先是两者都应该是全英文、英式英语……其次应该要按照我素材库中的模版直接生成并导出相同格式的 PDF 或 word，现在生成的内容都是全文字的，我还需要自己粘贴到模板中，自动化程度太低。」

最后那五个字是根因判断，不是抱怨。有了它，下一轮才知道该往哪个方向修。

Iterate：按复杂度分流到不同工具

四条迭代项分别标了 简单 中等 中等 复杂，并且指定了各自的做法。规则很清楚：

  • 简单的改文件。比如「生成内容必须为全英文、英式英语」这种，直接改 CLAUDE.md 的 Define 部分，用自然语言要求即可。
  • 中等及以上走 Plan Mode。涉及交互重做、跨模块统一、新增导出能力的，一律先出方案再动手。
  • UI 规范这类横切要求，写进 CLAUDE.md，作为「后续所有模块改动的统一依据」——又一次「固化成机制」。
贯穿全程

七条硬规范

事实依据Define 写进 CLAUDE.md，成为项目的唯一事实来源，所有后续 prompt 回指它。
先想后做Plan Mode 出方案 → 人工 review → 才执行。每个模块无一例外。
依赖顺序基础链路 → 信息库 → 素材库 → 进展记录 → 生成。先打通读写，再做业务。
模块节奏看 Plan → 生成 → 本地验证 → commit。固定四拍。
清空上下文换模块前清空。避免上一个模块的决定污染下一个。
真实路径验证「验证应用本身（不是靠 CLI/SQL Editor）能真实地正常读写这 7 张表」——不用捷径验证，捷径能过不代表用户路径能过。
记录不做什么Reflect 阶段明确写下本次不做的事项及理由，留给下一轮，而不是默默消失。
落到我们项目

我们该补的是 Define

诚实对照 我们目前有：一段 Problem/Idea 的收窄（符合规范）、一个能跑的原型、一份对内定位文档。
我们缺的是：Define 五件套（尤其是可判定的验收标准）、CLAUDE.md（把 Define 固化成事实依据）、工具选型（现在的单文件 HTML 是权宜之计，不是选型结论）。
后果很具体：每次对话我都要重新交代一遍上下文，而且没有任何一条约束是被机制守着的——全是口头约定。

下一步直接可用的 prompt

按 T1 填好的Define
基于我们已经收窄的开发目标——面向独居、生活经验有限人群的
极端天气行动清单（台风/暴雨单一天气，全时间轴，不接实时气象 API，
不做账号，不做聊天框）——帮我定义更清晰完整的问题描述。

请产出五块：
1. 目标用户：具体到一个人，不要写"独居脆弱人群"这种范畴词。
2. 核心模块：编号列出，每条说清呈现什么、数据从哪来。
3. User story：作为 X 我想 Y 这样 Z，Z 必须是收益不是动作。
4. 验收标准：逐条对应核心模块，每条都要可判定。
   其中必须包含负向禁止和流程约束，例如内容与官方预警冲突时
   如何处理、未经核对的条目能否展示。
5. 产出形式：形态、使用范围、未来是否要扩展到多天气/多城市。

只出定义，不要写代码，也不要建议技术选型——那是下一步的事。

Define 定稿之后，再按 T2 的骨架逐模块推进，第一个模块应该是「求助话术」而不是「行动清单」——因为按定位文档的判断，那才是核心机制，而且它依赖最少、能最快拿去做用户测试。

本卡片是对上述工作坊材料的方法提炼，引文均出自该材料，用于本项目内部复用。原项目（Job Hunt Copilot）的技术选型结论针对的是「需要关系型数据 + 文件存储 + 受约束生成」的全栈产品，与我们当前的静态原型不是同一类，可以照抄的是提需求的结构，不是选型结果。
