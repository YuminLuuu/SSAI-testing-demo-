01 · 背景

问题与机会

极端天气来临时，信息是不缺的——预警、科普、新闻推送都在。卡住人的是另外三件事：这些信息里哪一条跟我有关、现在这个小时我具体该做什么、这件事该不该我自己弄、不该的话找谁、怎么开口。

现有渠道各自解决了一部分：气象台发布权威预警，但它只到"发生什么"，不到"你该做什么"；科普内容按知识分类组织（什么是台风、中暑怎么办），而人在事发时是按时间和处境提问的；政务与社区服务能提供实际帮助，但用户往往不知道边界在哪，也开不了口。

对独居者、行动不便者、生活经验有限的人来说，这三个缺口的代价被放大：没有人替他们做判断，没有人顺手帮一把，也没有人在他们出事时立刻发现。

产品主张 不是知识库，是一份会根据你今天的处境变化的行动清单；并且把「该找谁 + 怎么开口」当成和应对知识同等重要的内容来做。
前提说明 上述判断目前是假设，未经用户访谈验证。本文档中所有需求的优先级都建立在这个假设之上；假设被证伪时，第 15 节的停止条件生效。
02 · 用户

目标用户与他们要完成的事

三类主要用户，共同点不是身份标签，而是缺少可以立刻调用的外部帮助。

主要用户 1

独居、生活经验有限

多为独自租住的年轻人。第一次遇到台风停水停电、房屋渗水，不知道哪些事该找物业、哪些该找房东、哪些要自己扛，也担心开口麻烦别人。

"我不知道这算不算大事，也不知道该打给谁。"

主要用户 2

行动不便 / 使用轮椅

日常出行高度依赖坡道、电梯、无障碍通道。极端天气会同时让这些设施失效，平时最优的那条路线在当天可能完全不可用。

"停电了电梯就停，我在楼上下不来。"

主要用户 3

慢性病 / 恢复期独居者

骤冷骤热会直接加重身体负担，用药和就医安排会被天气打乱；紧急时刻需要能一次性说清自己的健康信息。

"真出事的时候，我说不清我在吃什么药。"

次要用户

关心他们的人

家人、朋友、社区工作者。他们不是使用主体，但是"报平安"和"紧急信息卡"两个机制的另一端，产品设计必须把他们算进去。

用户要完成的事（按优先级）

  1. 搞清楚这次跟我有没有关系，以及严重到什么程度需要改变今天的安排。
  2. 拿到此刻能照做的三到五件事，而不是一篇需要自己提炼的科普。
  3. 判断这件事该不该我自己做；不该的话，知道找谁、什么时候找、第一句话怎么说。
  4. 今天这条路还能不能走——对依赖无障碍设施的人，这是每天都要问的问题。
  5. 把身体状况留下痕迹，以便下次跟医生说清楚，或在紧急时刻一次性交出去。
03 · 边界

产品定位与明确不做的事

产品作用在气候适应（adaptation）框架里的一个很窄的位置：不改变致灾因子、暴露度和个体敏感性，只补齐适应能力里的知识／技能与社会资本两项。这条边界同时是一条能拒绝需求的判据——任何不作用在这两项上的功能想法，都应排到很后面。

非目标 1明确不做
不发布预警，不替代官方渠道
产品任何时候都不得与官方预警相矛盾，并始终提供官方渠道的出口。预警的权威解释权在气象与应急部门。
非目标 2明确不做
不做医疗诊断
健康笔记是记录与整理工具，不产生诊断结论、不给用药建议。涉及药物的内容一律指向"问开药的医生或药师"。
非目标 3明确不做
不做社交网络
路径 B 是信息互填，不是社区。没有关注、没有主页、没有私信。降低运营与内容审核成本，也避免把求助变成表演。
非目标 4明确不做
不追求日活
极端天气一年发生几次，日活会逼产品往"每天来打开一下"的方向加功能，而那些功能一定和核心机制无关。指标见第 12 节。
04 · 架构

信息架构

三条并列路径 + 一个常驻功能。三条路径的时间尺度不同，这是它们并列而不是合并的原因：A 是事件驱动（一年几次），B 是日常（可能每天），C 是长期（周与月）。常驻紧急求助横跨三者。

├─ 路径 A · 天气应对 事件驱动 │ ├─ 选择当前天气情境（高温 / 暴雨 / 台风 / 寒潮） │ ├─ 补充个人情况（外出 · 身体状态 · 是否独居 · 行动能力 · 出行需求） │ ├─ 今日行动建议：当前风险 → 与我有关的影响 → 现在先做什么 │ │ └─ 3–5 条优先行动 · 朗读 · 放大字号 · 继续提问 │ └─ 延伸：收藏 / 标记完成 · 更详细说明 · 跳转紧急求助 │ ├─ 路径 B · 日常无障碍资源 日常 │ ├─ 浏览（路不好走 / 通道被占 / 电梯停运 / 其他） │ ├─ 按地点 · 类型 · 更新时间 · 是否仍有效筛选 │ ├─ 用户补一条新情况 · 标记是否已失效 │ └─ 延伸：收藏常用地点 │ ├─ 路径 C · 个性化健康笔记本 长期 │ ├─ 查看记录（身体反应 / 出行天气 / 用药 / 就医康复） │ ├─ 新增一条（发生什么 · 身体反应 · 是否与天气有关 · 是否需关注） │ ├─ 系统整理：周期提醒 · 阶段总结 · 风险提示 │ └─ 延伸：生成紧急信息卡 │ └─ 常驻 · 紧急求助 全局 ├─ 110 / 119 / 120 / 物业 · 社区 · 紧急联系人 ├─ 现在先做什么 · 不要做什么 · 需要联系谁 └─ 紧急信息卡：基本情况 · 行动能力 · 健康用药 · 紧急联系人
跨路径的数据流 路径 A 的个人情况与路径 C 的用药与就医记录自动带入紧急信息卡；路径 A 的当前情境决定紧急页的行动提示内容。这三条连线是产品成立的关键——否则三条路径只是拼在一起的三个 App。
05 · 功能需求

路径 A · 天气应对

四个情境：高温／热浪、暴雨／内涝、台风／强风、寒潮／极端低温。这条路径是产品的主线，也是三条路径里唯一在事件发生时被外部事件唤起的。

A-1P0原型已实现
选择当前天气情境
四选一，每个情境带一句体感描述（"体感闷、夜里也不降温"），让用户按感受而不是气象术语来选。
验收标准
  • 四个情境入口在首屏同时可见，不需要滚动或展开
  • 选择后可随时返回更换，已填的个人情况不丢失
A-2P0原型已实现
补充个人情况（五个问题）
今天是否外出／通勤、当前身体状态、是否独居、行动能力、今天有什么非出门不可的事（可多选）。全部可跳过，可随时修改。
验收标准
  • 五个问题都能跳过，跳过后仍能拿到通用版建议，并明确标注"这是通用版"
  • 答案在本地持久化，下次进入不需重填
  • 问题措辞不使用医学或残障术语，用第一人称日常说法
A-3P0原型已实现
今日行动建议的三段阅读结构
固定顺序：当前风险 → 与我有关的影响 → 现在先做什么。这个顺序本身是产品观点——先解释风险的性质（而非严重程度打分），再落到"我"，最后才给动作。
验收标准
  • 三段顺序固定，不可因排版原因调换
  • "现在先做什么"始终指向清单里第一条未完成的行动
A-4P0原型已实现
个性化的影响段
"与我有关的影响"由情境 × 个人情况实时拼装，不是固定文案。例：轮椅 + 暴雨 → "积水会让轮椅打滑并卡住前轮，盲道和路缘坡在水下看不见"。
验收标准
  • 改动任一个人情况，影响段的内容可见地变化
  • 未填个人情况时给出诚实的兜底文案，不假装个性化
  • 每条影响必须落到具体后果，不允许"请注意安全"一类空话
A-5P0原型已实现
3–5 条优先行动 + 动作卡固定字段
按优先级排序，因个人情况新增的条目要标出来源。每张动作卡的字段固定：动作 / 为什么 / 怎么做 / 耗时与花费 / 这事该不该我自己做 / 最常见的错 / 做完怎么算对。
验收标准
  • 七个字段缺一不可；没有内容的字段说明这条动作卡还没写完，不得上线
  • "该不该我自己做"有四个取值：自己可以做 / 找物业社区 / 需要找人搭把手 / 情况不对就求助
  • "最常见的错"必须是具体的错误行为，不是"注意安全"
A-6P0原型已实现
朗读与放大字号
建议正文可整段朗读（中文语音），字号可一键放大。这两项对本产品不是辅助功能，是主功能——目标用户里有相当比例在视力受限或情况紧急时无法细读。
验收标准
  • 朗读可随时停止，切换页面时自动停止
  • 不支持语音合成的浏览器给出明确提示，不静默失败
  • 放大字号后布局不破，不出现横向滚动
A-7P1原型已实现
收藏与标记完成
收藏跨情境汇总到一处；完成状态显示为"已完成 n / 共 m"。
验收标准
  • 刷新或关闭后状态保留
  • 勾选完成不隐藏条目，只降低视觉权重——用户需要能回头确认自己做过什么
A-8P1待决策
继续提问
原型为每个情境预置三个高频问题与固定回答，不接模型，页面上明确标注。是否接入 AI、以及如何把回答锁定在已核对语料内，见待决策 D-3。
验收标准（原型阶段）
  • 每条回答都标注"未经官方核对"与来源要求
  • 不假装是实时对话
A-9P1待实现
时间阶段分段（T-72h / T-24h / 进行中 / 灾后）
v0.1 原型按时间阶段组织台风清单，v0.2 扩到四个情境时暂未纳入。这是已知的功能回退：暴雨和寒潮同样有明确的时间轴，高温则更接近持续状态。
验收标准
  • 需先确认：四个情境是否都适用同一套时间分段，还是各自不同
  • 访谈中重点验证：用户是按"现在几点"还是按"现在什么情况"来找信息
A-10P1待决策
接入真实预警与定位
当前由用户自选情境。接入定位与气象预警可以省掉一步，但引入授权成本、离线不可用、以及与官方口径不一致的风险。见待决策 D-2。
06 · 功能需求

路径 B · 日常无障碍资源

四类在地信息：路不好走／临时修路、无障碍通道被占用、电梯停运／故障、其他在地信息。这条路径的价值密度取决于信息新鲜度，而不是信息总量。

B-1P0原型已实现
浏览与筛选
按类型筛选，按更新时间或确认次数排序，可只看仍有效的、只看收藏地点的。
验收标准
  • 每条信息必须同时显示：更新时间、提供者、"还在／已恢复"的计数
  • 已失效的信息降低视觉权重但不删除——"上周这里修好了"本身是有用的信息
B-2P0原型已实现
用户报一条新情况
四个字段：类型、地点、看到了什么、补充一句。只有前两项必填。
验收标准
  • 提交路径不超过三步，一只手可完成
  • 文案明确"写你亲眼看到的就够，不用写全"，降低提交门槛
B-3P0原型已实现
有效性标记
"今天还是这样"与"已经恢复了"两个按钮直接改变状态与计数，不需要评论、不需要注册。
验收标准
  • 一次点击即生效，并立刻刷新更新时间
  • 信息超过一定时长无人确认时自动标为"待确认"（阈值待定）
B-4P0待实现
内容审核与滥用防护
用户生成内容一旦联网就需要处理：错误信息、恶意信息、涉及具体住址的隐私风险。原型阶段全部为本地数据，不涉及；联网前必须先有方案。
验收标准
  • 有举报入口与下架机制
  • 地点粒度不精确到门牌与个人住址
  • 明确标注"非官方数据"，且不得用于替代官方通告
B-5P0待决策
数据来源与冷启动
纯用户互填时，没人填这条路径就是空的。是否接入官方或第三方无障碍数据，见待决策 D-4。这一条同时关系到第 15 节的停止条件之一。
B-6P1待实现
结构化地点
当前地点是自由文本，无法按距离排序或做"我附近"。需要结构化后才能支撑真实使用。
07 · 功能需求

路径 C · 个性化健康笔记本

四类记录：身体反应、出行／天气影响、用药、就医／康复。它的价值出口不在"记录"本身，而在两个交付时刻：下次跟医生说清楚，以及紧急时刻一次性交出去。

C-1P0原型已实现
记录列表与筛选
按四类筛选，另有"需要后续关注"一个横切筛选项。
验收标准
  • 与天气／出行有关的记录有独立标记，可被路径 A 复用
  • 记录可删除，删除不需要二次确认之外的任何流程
C-2P0原型已实现
新增一条记录（四个问题）
今天遇到了什么情况 / 身体有什么反应 / 是否与天气·出行有关 / 是否需要后续关注。只有第一项必填。
验收标准
  • 能在 30 秒内完成一条记录
  • 不要求填时间——系统自动记，用户在难受的时候不该被表单为难
C-3P1原型已实现
阶段总结
由记录实时计算：最近两周条数、其中与天气相关的比例、标记为需后续关注的条数。连续出现天气相关不适时，反向提示用户去把路径 A 的个人情况填全。
验收标准
  • 总结只做归纳与计数，不产生任何诊断性结论
  • 记录为空时说"还没有记录"，不编造总结
C-4P1待实现
周期提醒
服药、复查、量血压。原型中为固定示例项，真实版本需要用户自定义周期，并依赖系统通知能力（Web 端受限）。
验收标准
  • 提醒周期由用户设定，不预设任何医学频率
  • 复查提醒的时间基准来自用户自己的就医记录
C-5P0原型已实现
生成紧急信息卡
这是路径 C 与常驻紧急功能的连接点，也是这条路径最可能被验证成立的价值出口。详见 D-4。
C-6P2待决策
导出 / 同步给家人
健康数据是本产品里最敏感的一类。是否支持导出或同步，见待决策 D-5。
08 · 功能需求

常驻 · 紧急求助

全局常驻，任何页面一键可达。设计前提是：用这块功能的人处在最差的状态——可能看不清、说不出话、只有一只手、只有几秒钟。

D-1P0原型已实现
常驻入口与一键拨号
红色常驻按钮；紧急页给出 110 / 119 / 120 与紧急联系人四个入口，直接触发拨号。
验收标准
  • 入口在所有页面可见，且不遮挡正文最后一行
  • 号码字号足够大，误触率低；每个号码标注适用场景，不让用户临场判断打哪个
D-2P0原型已实现
情境化的紧急行动提示
三段固定结构：现在先做什么 / 不要做什么 / 需要联系谁。内容随路径 A 当前情境变化；未选情境时给通用版。
验收标准
  • 每段不超过三条，不需要用户判断，照做即可
  • "不要做什么"视觉上单独成块，与"要做什么"不可混淆
  • 这部分内容属于高危内容，必须逐条标注来源（见第 10 节）
D-3P0原型已实现
紧急信息卡
五个字段：姓名／称呼、基本情况、行动能力／辅助设备、重要健康信息／用药、紧急联系人。可编辑、可复制成文字。
验收标准
  • 未填写的字段显示为"未填写 —— 建议补上"，不隐藏
  • 卡片写给"完全不认识你的人"看，字段命名与排版按此校准
D-4P0原型已实现
跨路径自动带入
基本情况与行动能力来自路径 A 的个人情况；健康用药来自路径 C 最近的用药与就医记录。自动带入的内容明确标注"自动带入，建议核对后补充"。
验收标准
  • 用户手填的内容永远覆盖自动带入的内容

10 · 内容

内容规范与安全红线

当前状态 原型中的具体数字与处置方法全部是待核对的草稿。在给任何真实用户使用之前，必须逐条比对应急管理部门、当地气象台、红十字会的公开指引并标注来源。

四条红线

  1. 不得与官方预警相矛盾，并在每个情境页提供官方渠道出口。
  2. 高危内容必须有来源：涉水深度判断、中暑与热射病分界、失温与一氧化碳中毒识别、食物与药品安全、取暖设备使用。这几类写错会出事。
  3. 公开资料说法不一时，不给结论。原型的处理方式是明写"这一条公开资料说法不一，本产品不给结论"，并给出更可靠的替代做法（例：台风天窗户贴胶带）。
  4. 不给用药建议。所有涉药内容一律指向"问开药的医生或药师"，并提示不要自行停药。

内容写作规范

  • 判断标准用身体参照点，不用数字。"看不见底的水一律不过"优于"水深超过 X 厘米不要通过"——后者在现场无法测量。
  • "最常见的错"必须是具体行为，例如"风起来之后再去阳台收东西"，而不是"注意安全"。
  • 避开适应不良（maladaptation）建议：某些措施短期有效但长期加剧脆弱性，最典型的是高温时鼓励人人猛开空调。
  • 语言纪律：不使用"脆弱人群""弱势群体""适应能力"等对内术语，用户界面上一个字都不出现。
11 · 数据

数据与隐私

这个产品会收集三类数据，敏感度递增：路径 A 的个人情况（含行动能力与身体状态）、路径 B 的位置行为、路径 C 的健康记录。其中后两类在中国属于敏感个人信息，一旦联网即触发更严格的合规要求。

14 · 决策

待决策问题

以下六个问题在原型里都已按某种方式先行处理，但结论未定。每一条都写明了需要什么才能决定——多数需要访谈数据，而不是更多讨论。

D-1影响：整体信息架构
三条路径并列，还是天气应对为主、另两条收进二级？
现状首页三张卡片并列，各自显示当前状态。
取舍并列让另两条路径可被发现，但削弱了主线；收进二级则更聚焦，但路径 B、C 可能永远没人点。
需要访谈中观察用户第一次打开时先点哪一条，以及他们认为这三件事是不是一个产品。
D-2影响：A-10 · 技术架构
路径 A 要不要接真实预警数据与定位？
现状用户自己选情境，不依赖授权，离线可用。
取舍接入省掉一步、能做推送唤起（直接关系到 M1）；但引入定位授权流失、离线不可用、与官方口径不一致的风险。
需要确认气象数据的合规来源与授权方式；访谈中确认用户是否愿意为此授权定位。
D-3影响：A-8 · 内容安全
"继续提问"要不要接 AI？如果接，如何把回答锁死在已核对语料内？
现状预置问题 + 固定回答，页面明确标注不接模型。
取舍开放问答的体验明显更好，但高危内容一旦生成错误答案，代价是人身安全，且与第 10 节的红线直接冲突。
需要先完成 E-4 的内容溯源体系——没有已核对语料，就没有可以锁定的范围。
D-4影响：B-5 · 路径 B 是否成立
路径 B 的信息来源：纯用户互填，还是接入官方／第三方数据？
现状纯互填，原型内置 6 条种子数据。
取舍互填的独家性最高、成本最低，但冷启动阶段是空的；接入外部数据能解决冷启动，但那些数据的更新频率通常撑不起"今天这条路能不能走"。
需要先摸清有没有可用的超本地数据源。这条同时是停止条件之一（见第 15 节第 3 条）。
D-5影响：C-6 · 隐私立场
健康记录只留本地，还是支持导出／同步给家人？
现状只在本地，换设备不同步。
取舍换手机即丢失是真实的流失点，也让 M2（跨事件对比）无法测量；但联网存储健康数据会显著抬高合规门槛与信任成本。
需要访谈中确认用户对"健康记录上云"的接受度；优先考虑本地导出文件这种不需要服务端的折中方案。
D-6影响：D-5 · 紧急场景可达性
紧急信息卡要不要脱离 App 存在？
现状在 App 内展示，可复制成文字。
取舍真出事时人可能解不开锁、找不到 App，卡片再完整也交不出去。锁屏可见、可打印、二维码是三个候选方向，成本与形态差别很大。
需要先确认 M6——如果用户根本不填这张卡，这个问题不用回答。
15 · 证伪

风险与停止条件

这些不是风险清单，是预先写好的停止条件。写在前面，是为了到时候不会自己骗自己。

停止条件 1 访谈里没有人在事后做过任何准备动作。那说明"预防"是伪需求，我们只能做事发工具，市场和价值都小很多，整个定位要推倒重来。
停止条件 2 「该找谁 + 怎么开口」没有引起明显反应。那说明我们对这个人群的判断错了——她们卡住的地方不是社交成本，而是别的东西。这一块是最独特的假设，它塌了，差异化就塌了。
停止条件 3 找不到官方之外的独家数据来源。没有超本地的积水点、停电范围、社区级信息，产品就只是一个套壳的内容产品，会被免费且权威的官方渠道碾过去。
停止条件 4 个性化问题产生的差异，用户感知不到。那"因人而异"这个核心卖点不成立，产品会退化成一份精美的通用清单。

其他风险

  • 内容责任风险。高危内容出错的代价是人身安全。缓解方式是第 10 节的四条红线与 E-4 的溯源体系，二者缺一不可。
  • 三条路径互不相干的风险。如果跨路径的数据流（第 4 节）没有被用户感知到，产品会被当成三个独立小工具，留存与价值都会打折。
  • 无障碍做成"看起来无障碍"的风险。只做代码层面的 aria 与对比度、不做实机走查，等于没做。E-1 的最后一条是硬要求。

文档关系。本 PRD 的定位、指标与停止条件部分承自对内定位说明（docs/positioning.html，不对外使用）；功能范围承自路径树需求稿；实现状态对应可交互原型 app.html（v0.2）与 index.html（v0.1，台风单情境，保留作对照）。

本文档包含多项未验证假设。标注为「待决策」的条目在完成用户访谈前不应作为结论对外表述；标注为「原型已实现」指的是交互流程已跑通，不代表内容已核对。
